# 履历台：演示脚本

本项目是简历**归档辅助与人工复核**原型。演示数据和挑战集均为虚构文本；没有真实候选人资料、付费模型调用或自动录用/淘汰决策。[公开演示](https://guoge667.github.io/resume-review-desk/)无需登录，也可以使用 README 截图和本地运行。

## 3 分钟演示

1. **总览（30 秒）**：说明 10 份虚构简历进入页面后，有 8 份获得岗位建议、2 份待复核。所有建议仍需人确认。
2. **简历队列（60 秒）**：打开一条待复核记录，指出原文证据和升级原因；手动选择类别并写复核理由。再次打开可看到复核时间、规则版本、修改前后类别及当时的关键词快照。需要展示导出时，使用“导出复核日志”。导入文件及其复核刷新后清除；在“数据与边界”主动开启本机保存后，只能恢复内置虚构样本的复核与岗位规则。
3. **离线评测（60 秒）**：40 条固定挑战样本独立于首页演示与 25 条开发样本。原始规则完全一致 22/40、自动建议 21/40、错误建议 4 条；改进规则完全一致 37/40、自动建议 31/40、错误建议 1 条。重点展示剩余 3 条错误，以及覆盖率和建议正确率应一起看。
4. **Agent 回放（30 秒）**：选择 `F01` 看四个本地工具连续执行；选择 `B07` 看没有足够证据时跳过核验并升级；选择 `R06` 看否定语义仍可能导致的误判。展开每步输入输出，说明这是一条确定性工具编排轨迹，非 LLM 推理结果。

## 面试时可以回答的问题

- **为什么保留人工确认？** 关键词命中只说明文本出现了证据，无法证明候选人能力，也无法可靠理解跨岗位经历和否定语义。
- **为什么单列自动建议覆盖率？** 系统可以通过多给出“待复核”来提高已给建议的正确率，因此必须同时说明它给了多少建议。
- **Agent 部分真正实现了什么？** 四个可检查的本地工具、分支与跳过逻辑、失败时人工交接、逐步输入输出轨迹。没有调用模型，不应宣传为模型 Agent 的效果。
- **人工监督如何追溯？** 每次复核追加事件，保留当时的规则快照、原建议、修改前后结果、时间与理由；导出不含正文的日志。仅内置虚构样本可选择本机保存，不能当作防篡改的生产审计记录。
- **下一阶段如何改进？** 先建立有授权、独立标注的验证集，再研究隐私和公平性风险；若要对比模型，需要事先确定预算、指标与人工审批流程。

本地运行 `npm run test:e2e` 可重放“虚构 PDF 导入 → 查看证据 → 人工确认 → 导出日志”，并检查错误文件提示、内置虚构样本保存、导入文件刷新后清除和旧版快照清理。GitHub Pages 发布前也会运行功能测试和浏览器测试；这些只验证软件行为，不代表真实招聘准确率。

## 作品集表述

> 构建浏览器本地的简历归档与人工复核原型，支持 PDF/TXT/MD 文本读取、可编辑岗位规则、证据回溯、虚构样本复核的可选本机保存与逐次复核日志导出；用 25 条独立开发样本改进关键词规则，在固定 40 条虚构挑战案例上复测，将完全一致数从 22 提升到 37，错误自动建议从 4 条降到 1 条；实现四工具离线工作流回放与人工交接轨迹。导入文件不持久化，GitHub Pages 发布由自动测试把关；该原型不使用付费模型 API，评测结果不代表真实招聘准确率。
